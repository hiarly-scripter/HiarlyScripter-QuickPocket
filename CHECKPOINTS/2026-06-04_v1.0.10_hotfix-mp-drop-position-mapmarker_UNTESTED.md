## Bugs Corrigidos

### Bug P0-A: Drop do Player 2 aparecia perto do HOST

**Causa raiz confirmada (via log):**

`HandleHostDropRequest` chamava `PocketOperations.RestoreSnapshot(go, dropPos)` com a posição
correta do Player 2 (via `GetPositionByActorNumber`). Logo depois, publicava `QP_2=[]` nas Room
Properties → `OnRoomPropertiesUpdate` disparava → `ProcessRemotePocketUpdate(2, [])` → via "viewIDs
removidos", chamava `RestoreWithSafeDefaults(go, GetSafeDropPosition())` → `GetSafeDropPosition()`
retorna `PlayerAvatarLocal().position` = **posição do HOST** → sobrescrevia o restore correto.

**Evidência no log:**
```
[QP:MP] host drop actor=2 viewID=221 pos=(-4.25, 0.61, -2.80) result=OK
[QP] RestoreWithSafeDefaults em Item Health Pack Small(Clone)  ← SOBRESCREVEU!
```

**Fix:** `ProcessRemotePocketUpdate` retorna no início se `IsMasterClientOrSingleplayer()`.
O master gerencia todos os pockets via `_hostedPockets` diretamente.
`HideRemoteItem`/`RestoreWithSafeDefaults` no master são redundantes e conflitam com posição.

---

### Bug P1-B: MapMarker do TAB/minimap permanecia na posição original após drop (Player 2)

**Causa raiz:**

O host desabilita `snap.MapValuableSpriteRenderer.enabled = false` em `ApplyHide`. Mas o estado
de `SpriteRenderer.enabled` **não é sincronizado pelo Photon**. No cliente do Player 2, o
`SpriteRenderer` permanecia habilitado. `MapValuable.Logic()` (coroutine) continuava atualizando o
marker, mas o item estava em Y=-9999 — dependendo da lógica de clamping do MapValuable, o marker
ficava congelado na posição original pré-pocket.

**Fix:**
- `HandleClientPocketAck`: chama `ClientHideMapValuable(vid)` → desabilita SpriteRenderer local
- `HandleClientDropAck`: chama `ClientRestoreMapValuable(vid)` → reabilita SpriteRenderer local
- `MapValuable.Logic()` nunca foi interrompida (só o SpriteRenderer era desabilitado),
  então quando reabilitado, o marker já estará na posição correta

---

### Bug P2-C: Warnings "Setting linear velocity of a kinematic body" em massa

**Causa raiz:**

`HideRemoteItem` setava `rb.velocity=0` antes de verificar se `rb.isKinematic`. Quando o host
chamava `ApplyHide` (kinematic=true) e depois o `OnRoomPropertiesUpdate` disparava
`ProcessRemotePocketUpdate` → `HideRemoteItem` (rb já kinematic) → warning Unity.

**Fix:** Adicionado guard `if (!rb.isKinematic)` antes de setar velocity em `HideRemoteItem`.
Com o Fix-A (master skip), este path não executa no master. Fix mantido para não-master.
